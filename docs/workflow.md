# 개발 작업 흐름

## 작업 인계 기록

- 작업할 때마다 루트의 `HANDOFF.md`를 읽고, 진행한 내용을 한국어로 기록한다.
- `HANDOFF.md`는 `이전 내용 요약`과 `현재 진행 내용` 두 섹션으로 관리한다.
- 새 작업을 시작할 때 기존 기록을 읽고, 다음 작업에 필요한 맥락만 `이전 내용 요약`에 통합한다. 요약한 과거 상세 기록은 삭제하고 `현재 진행 내용`을 새 작업의 기록으로 교체한다.
- `현재 진행 내용`에는 이번 작업의 진행 상황과 결과, 미해결 사항, 다음 작업에 필요한 내용을 간결하게 남긴다.
- 모든 작업 이력을 누적하지 않는다. 코드만으로 알 수 있는 구현 설명은 중복 기록하지 말고, 작업을 이어가는 데 필요한 맥락을 남긴다.
- 작업 중 의미 있는 진척이나 변경 사항이 생기면 기록을 갱신하고, 커밋 전과 작업 종료 전에 최신 상태인지 확인한다.

## 커밋과 푸시

- 코드나 문서 수정이 의미 있는 작업 단위로 진행되면, 전체 작업이 끝날 때까지 미루지 말고 커밋하고 푸시한다.
- 커밋 전에 diff를 검토하고, 같은 목적이나 기능에 관련된 변경을 하나의 커밋으로 묶는다. 서로 무관한 변경은 별도 커밋으로 나눈다.
- 커밋 메시지는 한국어로 작성하며, 변경 내용과 목적을 명확하게 설명한다.
- 각 커밋 전에 변경에 필요한 검증을 수행하고 결과를 확인한다.
- 커밋 후 작업 브랜치를 원격 저장소에 푸시한다.
- 커밋과 푸시를 완료한 뒤에는 반드시 사용자에게 실제 커밋 메시지와 함께 푸시 완료 사실을 알린다. 여러 커밋을 푸시했다면 각 커밋 메시지를 알린다.
- 관련 없는 기존 변경은 임의로 포함하거나 되돌리지 않는다.
- 커밋이나 푸시가 실패하면 원인을 확인하고, 해결하지 못한 경우 실패 사실과 원인을 사용자에게 알린다.

## 배포와 결과 확인

- 사용자가 달리 요청하지 않는 한, 검증을 마친 화면·기능 변경은 에이전트가 공개 배포까지 진행한다. 사용자가 매번 수동으로 배포 버튼을 누르는 절차를 요구하지 않는다.
- 작업 브랜치에 푸시하는 것과 배포를 구분한다. 공개할 변경은 기존 이력을 보존하며 배포 대상 브랜치에 반영한다. 실제 배포 조건은 [배포 워크플로](../.github/workflows/deploy.yml)를 참조한다.
- 자동 배포의 실행 결과를 확인하고 사용자에게 알린다. 권한이나 도구의 제약으로 결과를 확인하지 못하면, 푸시 완료와 배포 성공을 구분해 확인하지 못한 상태를 명시한다.
- 사용자 조작은 저장소 설정·권한 변경 등 에이전트가 직접 처리할 수 없는 경우에만 요청하고, 필요한 이유와 최소 단계를 설명한다. 최초 설정을 반복 작업으로 안내하지 않는다.
